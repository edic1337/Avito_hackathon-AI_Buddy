# Устройство ветки RAG и работа с корпусом

## Что уже работает

- Корпус из 827 публикаций каталога Avito на Хабре, 28 документов Playbook и 16 пунктов чек-листа.
- Markdown-парсер, сохранение пути заголовков и точный токенный бюджет.
- Обработка списков, кода, Markdown-таблиц и HTML-таблиц с контекстом строки/колонки.
- Qwen3-Embedding-0.6B: векторы из 1024 чисел, нормализация, отдельный prompt для вопросов.
- Пакетный экспорт в JSON версии 2, промежуточные файлы по документам и продолжение через `--resume`.
- Конфигурация из корневого `.env`, переменных процесса и параметров командной строки.
- SQL-схема PostgreSQL + pgvector и модульные проверки.

## За что отвечает код

| Модуль | Вход → результат | Граница ответственности |
| --- | --- | --- |
| `config.py` | `.env` + окружение → `RagConfig` | Не устанавливает CUDA, не подключается к БД, не печатает секреты |
| `models.py` | Структуры `Document`, `TextChunk`, `EmbeddedChunk`, `Chunk`, сообщения и события | `Chunk` со score предназначен для результатов поиска; `EmbeddedChunk` — для подготовленных данных |
| `interfaces.py` | `Protocol`-контракты внешних зависимостей | Объявления методов, а не работающие SQL/LLM реализации |
| `documents.py` | UTF-8 Markdown с YAML → `Document` | Требует title, source_url, origin и min_role; отклоняет неоднозначные метаданные |
| `chunking.py` | `Document` + токенизатор → `list[TextChunk]` | Разделы не смешиваются; код и таблицы обрабатываются отдельно; считает точную строку для эмбеддинга |
| `embeddings.py` | Строки → нормированные векторы 1024 | Загружает одну модель лениво; сериализует обращения к ней; проверяет размерность и конечность чисел |
| `ingestion.py` | Файл → документ и готовые чанки с векторами | Составляет шаги для одного документа; SQL-записи нет |
| `export_corpus.py` | Папка `.md` → JSON | Адаптер публичных статей, HTML-нормализация, длинные ячейки, хеши, checkpoints, сборка и отчёт об ошибках |
| `demo_chunking.py` | Один файл → вывод / JSON версии 1 | Локальная диагностика. `--plain` означает тестовое происхождение, не производственный импорт |
| `demo_embeddings.py` | Два тестовых текста и вопрос → векторы и скалярные сходства | Позволяет проверить модель и query-prompt без PostgreSQL |

## Путь данных

```text
Markdown + YAML
  → load_source / parse_document
  → Document
  → нормализация HTML для чанкинга
  → CorpusChunker / MarkdownChunker
  → TextChunk(section, text)
  → embedding_text = "Название | Путь раздела\nТекст"
  → QwenEmbedder.embed_documents
  → 1024 координаты на чанк
  → промежуточный JSON документа
  → итоговый JSON корпуса
  → будущий импортёр → PostgreSQL
```

Вопросы кодируются через `embed_query`: та же модель и размерность, но с query-промптом. После реализации поиска вектор вопроса будет сравниваться с векторами чанков; фильтрация role/team должна выполняться до итогового top-k. Порог близости не является вероятностью правильного ответа и требует проверки на вопросах из вашей предметной области.

## Данные и метаданные

В наборе Хабра есть совместные публикации других компаний, перечисленные в каталоге Avito. Исходные URL сохраняются, поэтому источник может отличаться от `/companies/avito/`.

| Значение origin | Смысл |
| --- | --- |
| `public` | Публичная веб-публикация |
| `provided` | Реальный файл, предоставленный пользователем; это не заявление о его публикации в интернете |
| `synthetic` | Созданный для разработки тестовый материал |

У всех подготовленных реальных материалов указан `min_role=intern`, `team=null`. Чек-лист предназначен для общей базы материалов стажировки. Роли исполнителей задач не вычисляются из текста автоматически; повторяющиеся записи не удаляются.

## Настройки `.env`

Приоритет: **значения кода < `.env` < переменные процесса**. Для устройства CLI `--device` дополнительно переопределяет конфигурацию.

`RagConfig.from_env()` находит `.env` рядом с корневым README по расположению самого кода, независимо от текущей папки терминала. Он читает значения, не изменяя глобальное `os.environ`. Для изолированных тестов и управляемого запуска есть `RagConfig.from_env(env_file=None)`.

Шаблон `.env.example` находится в Git. Настоящий `.env` создаётся на каждом ПК отдельно, остаётся в `.gitignore` и не передаётся в репозиторий. Секреты вводятся локально. Символ `$` в значениях считается буквальным; подстановка `${NAME}` отключена. Пароль в URL при необходимости кодируется по правилам URL.

| Группа | Настройки | Применение |
| --- | --- | --- |
| Эмбеддинги | `EMBEDDING_MODEL`, `EMBEDDING_DEVICE`, `EMBEDDING_BATCH_SIZE` | Работают сейчас; по умолчанию CPU и батч 8 |
| Токенизатор | `TOKENIZER_MODEL` | Необязателен: автоматически следует за EMBEDDING_MODEL |
| Чанкинг | `CHUNK_TARGET_TOKENS`, `CHUNK_MAX_TOKENS`, `CHUNK_OVERLAP_TOKENS` | 300 / 400 / 40; требуется overlap < target <= max |
| БД | `DATABASE_URL` | Сохраняется в конфигурации; подключение и импортёр ещё предстоит написать |
| Поиск | `TOP_K`, `MIN_SIMILARITY`, `CONTEXT_TOKEN_BUDGET` | 6 / 0.45 / 3000; будущие retrieval-компоненты |
| Дополнительные стадии | `USE_RERANKER`, `USE_QUERY_REWRITE` | Переключатели зарезервированы; самих реализаций нет |
| LLM | `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_MOCK` | Зарезервированы для будущего клиента |

Переменные Hugging Face вроде `HF_HUB_OFFLINE` относятся к внешней библиотеке: задавайте их в процессе PowerShell, а не рассчитывайте на применение через `RagConfig`. Для загрузки токенизатора из кеша экспортёр поддерживает `--offline`; для полностью офлайн-работы модели также задайте `$env:HF_HUB_OFFLINE='1'` после скачивания весов.

## Перенос на другой Windows-ПК

Из корня клонированного репозитория:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
```

Выберите **один** вариант PyTorch:

```powershell
# Обычный CPU
.\.venv\Scripts\python.exe -m pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cpu

# Или NVIDIA GPU с совместимым драйвером
.\.venv\Scripts\python.exe -m pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cu128
```

Затем:

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe -m pip check
if (!(Test-Path .env)) { Copy-Item .env.example .env }
notepad .env
.\.venv\Scripts\python.exe -m unittest discover -s backend/tests -v
```

В `.env` оставьте `EMBEDDING_DEVICE=cpu` для обычного ПК или укажите `cuda` для GPU. Файл настроек не устанавливает драйвер и CUDA-сборку PyTorch. Проверка GPU:

```powershell
.\.venv\Scripts\python.exe -c "import torch; assert torch.cuda.is_available(); print(torch.cuda.get_device_name(0)); print(torch.ones(1,device='cuda'))"
```

Интернет нужен на новом ПК для зависимостей и первоначальной загрузки Qwen. Модель не обучается и статьи не отправляются во внешний LLM API: здесь выполняется локальный расчёт векторов.

## Основные команды

```powershell
# Сначала проверить разбиение, не рассчитывая векторы
.\.venv\Scripts\python.exe -m backend.rag.export_corpus --input data/kb/onboarding --output embeddings/onboarding-chunks.json --chunks-only --resume --fail-fast

# Playbook + чек-лист: 44 документа / 780 чанков
.\.venv\Scripts\python.exe -u -m backend.rag.export_corpus --input data/kb/onboarding --output embeddings/onboarding-corpus.json --resume --fail-fast

# Хабр: 827 документов / 15 633 чанка
.\.venv\Scripts\python.exe -u -m backend.rag.export_corpus --input data/kb/habr --output embeddings/habr-corpus.json --public-habr --resume --fail-fast
```

Устройство берётся из `.env`; для разового переопределения допишите `--device cpu` или `--device cuda`. На текущем ПК с настроенным системным Python допустим `python` вместо пути к `.venv`.

Ожидаемые количества относятся к текущему набору и настройкам 300/400/40. Изменение текстов, настроек или токенизатора может изменить число чанков.

`--public-habr` нужен только файлам Хабра: адаптер дополняет публичные метаданные. Для Playbook и чек-листа все поля уже подготовлены. `--chunks-only` не создаёт векторы; такой результат нельзя загружать в колонку `vector(1024)`.

По умолчанию оба набора используют одинаковое имя коллекции `avito-habr`, что сохраняет совместимость с уже посчитанным файлом. У наборов разные source_key, поэтому импортёр может объединить их в одну коллекцию при совпадающих настройках. Другую коллекцию можно указать через `--collection-name`; новые модель/правила требуют новой индексации.

## Готовые результаты и продолжение

Для передачи коллеге с БД нужны **оба** файла: `habr-corpus.json` и `onboarding-corpus.json`. Суммарно это 871 документ и 16 413 чанков с векторами. Повторный расчёт для загрузки JSON в БД не требуется.

Экспортёр сохраняет документ после завершения всех его батчей. `--resume` использует только совпадающий отпечаток исходника и конфигурации. Если вычисление прервано, незавершённый документ обрабатывается заново. Итоговый JSON собирается в конце потоково и заменяется атомарно.

После ошибки проверяйте `errors`, `summary.complete` и код завершения. Принудительное закрытие до сборки может оставить предыдущий итоговый JSON. Наличие файла само по себе не доказывает завершённость нового прогона.

Перед импортом требуйте `summary.complete=true`, `errors=[]`, `collection.embeddings_included=true`, по 1024 конечных числа в каждом векторе и норму около 1. Схема JSON подробно описана в [EXPORT_FORMAT.md](EXPORT_FORMAT.md).

## Проверки

Тесты `test_chunking.py`, `test_embeddings.py`, `test_export_corpus.py`, `test_provided_sources.py`, `test_env_config.py` проверяют структуру, Unicode, лимиты, код, таблицы, метаданные, корректность векторов, сериализацию и приоритет настроек. Большинство используют маленький тестовый токенизатор и тестовую модель, поэтому не требуют загрузки весов.

`check_chunking_qwen.py` — отдельная проверка с настоящим токенизатором. Полнота выгрузки и корректность векторов не доказывают качество поиска: для него ещё нужен набор контрольных вопросов и измерение retrieval.
